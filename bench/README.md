# Jevを挟む前と後を実測する

Jevを入れた理由が本当に成り立っているかを、同じ文書・同じプロンプトで確かめる。

```bash
# 実測（鍵が要る）
TYPESAFE_API_KEY=... OPENAI_API_KEY=... npm run bench
npm run bench:report          # → docs/jev-benchmark.md

# 配線だけ確かめる（鍵が要らない。測定値ではない）
node bench/run.mjs --mock
node bench/report.mjs         # → bench/results/mock-*.md
```

## 測るもの

| | 何を見るか |
|---|---|
| 最初の反応が出るまで | 書いていて、いつ反応が返るか |
| 一通り見終わるまで | 一度見るのに、いくら時間がかかるか |
| **1文直したあとの更新** | **直したら、いつスコアが変わるか** |
| トークンと費用 | 生成モデルに何を払っているか |
| precision / recall / F1 | 手を入れるべき文を当てられたか |

3つ目が本題。1文直すたびに全文を生成モデルへ送り直す作りだと、更新は常に
全文ぶんかかる。文単位で判定できるなら、更新は1文ぶんで済む。

## 決めていること

- **プロンプトは画面と同じものを読む**（`src/config/analyzePrompt.js`）。ベンチが似せた
  プロンプトを自前で持つと、測っているものが本番から少しずつずれていく。
- **応答の読み方も画面と同じ**にする。ここだけ寛容にすると、画面が捨てている応答を
  ベンチが拾い、指摘の件数が実際より多く出る。
- **コーパスは手書き**（`corpus.ja.json`）。生成モデルにも辞書にも作らせていない。
  作らせると、測る側と測られる側が同じ思い込みを共有してしまう。
- **文書に組んでから測る。** 今のアプリは本文を丸ごと渡しているので、文を1つずつ
  投げて比べると実際に払っているコストと合わない。組んだあと、文に割り戻せることを
  必ず確かめている（割り戻せないと、goldと予測の対応がずれる）。
- **単価の分からないものは費用を出さない。** 0として足すと、合計が安いほうに寄る。
  Jevの単価は `JEV_PRICE_INPUT` / `JEV_PRICE_OUTPUT`（100万トークンあたりUSD）で渡す。
- **`--mock` の出力は `docs/` に書かない。** 書けるようにすると、いつか偽の数字が
  レポートの顔になる。モックでは精度の表そのものを出さない。

## 選べるもの

```
--repeat=3          繰り返し回数（p50/p95を取る）
--model=<id>        生成モデル（既定はアプリと同じ DEFAULT_MODEL_ID）
--sizes=8,20,40     文書ごとの文数
--mock              記録した応答で回す
--out=path.json     出力先
```
