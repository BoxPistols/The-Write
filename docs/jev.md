# Jev（TypeSafe AI）の使いどころ

Jevは文章を書かない。型の付いた判定だけを返す。
このアプリでの役割は一つで、**生成モデルに渡す前に、手を入れるべき文を選ぶこと**にある。

## なぜ入れるのか

今の校正は、本文を丸ごと生成モデルに渡し、指摘の一覧をJSONで書かせている。
この作り方には二つの無駄がある。

1. **直す必要のない文にも生成のコストと時間がかかる。** 指摘が出るのは一部の文なのに、
   全文ぶんの入力トークンと出力トークンを毎回払っている。
2. **入力中には使えない。** 1000文字で4〜5秒かかるので、打鍵に追従できない。
   結果として利用者は「書き終えてからボタンを押す」しかなく、違和感は最後にまとめて出る。

Jevは文章を作らないので、1文の判定が生成の1往復より桁で速い。
そこで、**判定はJev、書き換えは生成モデル**に分ける。

## 何を尋ねているか

`src/config/jevQuestions.js` に置いてある。質問の形は3つしかない。

| 名前 | 形 | 何を返すか |
|---|---|---|
| `awkward` | `score` | 違和感の段階（0〜4の期待値）＋確率分布 |
| `aiLike` | `noul` | AI特有の型にはまっている確率（0〜1） |
| `kind` | `choice` | 手を入れる区分（grammar / spelling / … / none）＋確率分布 |

文字数、語尾の連続、和欧間スペースのように**数えれば分かるもの**はJevに尋ねない。
数えられることに確率を使うと、遅くなるうえに答えが揺れる。
その手の検査は既存の辞書（`src/utils/deadCliche.js`）が決定論的に担う。

判定に前後の文を添えているのは、指示語や省略された主語を「不明瞭」と誤って
落とさないため。前後まで直させたいわけではないので、stateの見出しで分けている。

## どこから指摘とみなすか

閾値は `FLAG_THRESHOLD` / `GATE_THRESHOLD` の2か所にまとめてあり、他に散らさない。
実測で動かす前提の数値だからで、散らすと動かせなくなる。

確率が割れている判定（`confidence` が低い）は、値が高くても指摘に格上げしない。
当てずっぽうと区別が付かない指摘で下線を引くと、利用者が指摘そのものを信じなくなる。

## 二つの関門

- **前段（トリアージ）** — 文ごとに判定し、フラグの立った文だけを生成モデルへ送る。
- **後段（検証ゲート）** — 生成モデルの書き換えを、原文と並べてJevに再判定させる。
  「自然になったか」と「意味が保たれているか」は**別に**尋ねる。まとめて尋ねると、
  自然だが数値の変わった書き換えを通してしまう。意味の保持のほうを厳しく取る。

## 契約

エンドポイントは `POST /v1/systemone` の1本だけ。
公式SDK（`@typesafe-ai/sdk`）は入れず、`api/_jev.js` に素のfetchで書いている。
他のプロバイダーを `api/_shared.js` が同じ形で扱っているため、ここだけSDKに寄せると
読み口が割れるわりに、省けるのはリトライとタイムアウトの数十行だけになる。

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer $TYPESAFE_API_KEY

{ "model": "jev-latest", "state": <文字列 or JSON>, "questions": { "<名前>": <質問> } }
→ { "model": "...", "answers": { "<名前>": <答え> }, "usage": { "input_tokens": n, "output_tokens": n } }
```

答えの形は質問の形で決まる。

- `noul` → `{ type, noul }`
- `choice` → `{ type, choice, confidence, probabilities }`
- `score` → `{ type, score, confidence, legend, probabilities }`

## 鍵が無いとき

`TYPESAFE_API_KEY` が無ければ `/api/providers` の `jev` が `false` になり、
判定の下線とトリアージが止まる。アプリの他の機能はそのまま動く。
